# Semaphore / Tornado Cash / Privacy Pools のルート履歴の仕組み

各実装がオンチェーンで「どの Merkle ルートに対する証明を受け付けるか」をソースコードで確認した。

| 実装 | 確認したコード | 古いルートの扱い | Δ の単位 |
|---|---|---|---|
| Tornado Cash | tornado-core `MerkleTreeWithHistory.sol`（commit 1ef6a26, 2022-03） | 直近 **30** 個のルートをリングバッファで保持し、どれでも受理 | **更新回数**（30回） |
| Semaphore v4 | semaphore `Semaphore.sol`（commit 38d9908, 2026-09-18） | ルートが置き換えられた時刻を記録し、**置き換えから `merkleTreeDuration` 未満**なら受理。既定は **1時間**、グループ管理者が変更可 | **時間**（既定1時間） |
| Privacy Pools（0xbow） | privacy-pools-core `State.sol`, `PrivacyPool.sol`（commit d494b63, 2026-09-23） | 預け入れツリー: 直近 **64** 個。ASP ルート: **最新のみ** | 預け入れ: 更新回数 / ASP: 0（次の更新まで） |

## 1. Tornado Cash（件数ベース）
```solidity
uint32 public constant ROOT_HISTORY_SIZE = 30;
...
function isKnownRoot(bytes32 _root) public view returns (bool) {
  // roots[] を currentRootIndex から逆順に 30 件たどって一致すれば true
}
```
- 預け入れのたびにルートが変わるので、証明を作っている間に他人が預け入れても失敗しないよう、過去30個を許容している（**可用性のための設計**）。
- Tornado Cash は「追加のみ」のツリーなので、古いルートを許しても安全性は崩れない（古いルートに含まれていた預け入れは今も有効）。
- **しかし同じ設計を「非掲載証明」に流用すると危険**。非掲載は「追加で偽になる」性質（非単調）なので、古いルートを許すことがそのまま攻撃窓になる。
- 件数ベースの問題点: 実時間の Δ は**更新頻度に依存**する。更新が少ない期間は、1件の古いルートが何日も有効になりうる。逆に攻撃者が関係ない更新を大量に起こせるなら窓を縮めることはできるが、広げることはできない（上限 30 件分）。

## 2. Semaphore v4（時間ベース）
```solidity
// 古いルートは、置き換えられてから merkleTreeDuration が経過するまで受理
uint256 merkleRootSupersededDate = groups[groupId].merkleRootSupersededDates[proof.merkleTreeRoot];
if (merkleRootSupersededDate == 0) revert Semaphore__MerkleTreeRootIsNotPartOfTheGroup();
if (block.timestamp - merkleRootSupersededDate >= merkleTreeDuration) revert Semaphore__MerkleTreeRootIsExpired();
```
- `merkleRootSupersededDates` はメンバーの追加・更新・**削除**のたびに、置き換えられた古いルートに時刻を記録する（`Semaphore.sol` 86, 97, 113, 127 行目）。
- 既定の `merkleTreeDuration` は 1 hours（`createGroup` 36・44行目）。
- コード中のコメントが semaphore-protocol/semaphore issue #98 を参照している（経緯は未確認）。
- **本研究にとって重要な観察**: Semaphore ではメンバーを**削除（失効）**しても、削除前のルートで作った証明は最大 `merkleTreeDuration` の間は通る。つまり「失効の反映に Δ = 1時間の遅れがある」ことを、実装が仕様として受け入れている。これは匿名クレデンシャルの失効問題そのもの。
- 時間ベースの利点: Δ が実時間で上界を持つので、安全性の定義で扱いやすい。
- 注意: 「置き換え時刻から数える」ので、あるルートが長く最新のままだった場合、作成から見た有効期間は長くなる。本研究の Δ は「**掲載された時刻から**」測るべきで、Semaphore の定義（置き換えから）とは一致する。

## 3. Privacy Pools / 0xbow（ASP は最新のみ）
- ASP ルートは `latestRoot()` と一致しないと拒否。Δ ≈ 0 だが、ASP の更新ごとに作成済み証明が全部無効になる（詳細は 01 を参照）。
- 預け入れツリーは Tornado と同じく直近64個（追加のみなので安全）。

## 4. まとめ：本研究への示唆
1. 既存実装は「**追加のみの集合への所属証明**」のために古いルートを許しており、それ自体は安全。
2. 同じ「直近 N 個 / T 時間」を「**非掲載（除外）証明**」や「**削除を伴う所属証明**」に使うと、N 個 / T 時間がそのまま攻撃窓 Δ になる。Semaphore のメンバー削除はすでにこの状態。
3. Δ の測り方が実装ごとに違う（件数 / 時間 / 0）。**Δ を時間で定義し、件数ベースの方式は更新頻度を介して時間に換算する**のが比較の土台になる。
4. Δ = 0（Privacy Pools の ASP）は安全だが、可用性（証明の作り直し・送信中の失効）を犠牲にしている。→ 「Δ を小さくしてもコストが増えにくい方式」の需要は実在する。
